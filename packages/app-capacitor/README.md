# App Capacitor

The native iOS and Android shell for Balebase. It renders the shared
application from `packages/app` with a native host: requests carry the
WebView's origin marker, emailed links open the hosted app, and downloads go
to the system share sheet. Native releases require iOS 18 or later and
Android 12 (API 31) or later.

On Android, the page draws under the system bars when the WebView reports
safe-area insets (WebView 140 and later). Layouts pad themselves with the
insets, and the status bar sits on an ink band with light icons. The
navigation bar's icons follow the app's theme (`src/systemBars.ts`). Older
WebViews keep the page clear of the bars.

## Production and staging store apps

Native store releases have two targets backed by shared shell and Fastlane
configuration:

| Tier | Native app identifier | Android variant | iOS scheme / configuration |
| --- | --- | --- | --- |
| Production | `com.balebase.app` | `release` | `App` / `Release` |
| Staging | `com.balebase.staging.app` | `staging` | `App-Staging` / `Release-Staging` |

`NATIVE_RELEASE_TIER` (`production` by default) selects the tier.
`capacitor.config.ts` sets the app ID and name from it, and the Vite build
defaults `VITE_API_URL` and `VITE_APP_URL` to the tier's hosted API and app.
`fastlane/lib/native_release_target.rb` maps the tier to its Gradle variant,
Xcode scheme and configuration, and secrets folder. An unknown tier fails
before any lane runs.

Android staging inherits the release build type. Both iOS schemes are
committed and shared so Fastlane can archive either tier without relying on
Xcode's local autogenerated schemes.

## Set up

Install the pinned Ruby with mise, then the Fastlane bundle:

```sh
mise install
cd packages/app-capacitor
bundle install
```

## Releases

The Fastlane lanes live in `fastlane/`: `lanes/ios.rb`, `lanes/android.rb`,
`lanes/store.rb` for the lane outside a platform, and plain Ruby helpers in
`lib/`. Their tests are in `fastlane/test/` and run with `bun run test`.

| Lane | Does | Options |
| --- | --- | --- |
| `ios build_release` | Signed App Store IPA, without uploading | `build_number:` |
| `ios upload_release` | `build_release`, then uploads to TestFlight | `build_number:` |
| `ios profiles` | Creates or renews the match App Store profiles | `force:true` regenerates them |
| `ios fetch_profiles` | Installs the match App Store profiles read-only | |
| `android build_release` | Signed release App Bundle, without uploading | `build_number:` |
| `android upload_release` | `build_release`, then uploads to a Google Play track | `build_number:`, `track:` (`internal`), `release_status:` (`completed`) |
| `store_build_numbers` | Prints the latest build numbers in both stores | |
| `android build_debug_apk`, `android build_release_apk` | Builds an APK for sideloading | |
| `android install_debug`, `android install_release`, `android sideload` | Builds and installs an APK on a connected device | `build_type:release` (`sideload`) |
| `android test`, `android clean` | Runs the Android unit tests; cleans the build outputs | |

`build_number:` is the iOS build number or the Android version code. Without
it, a lane picks the next number as described under
[build numbers](#build-numbers).

Every lane but `android test` and `android clean` has a package script named
`<platform>:<lane in kebab case>`; `store_build_numbers` is
`store:build-numbers`. The iOS, App Bundle, and store build number scripts have
a `:staging` variant for the staging app. Every script sets
`NATIVE_RELEASE_TIER` itself, and arguments pass through to Fastlane:

```sh
bun run ios:build-release
bun run android:upload-release:staging track:alpha
bun run ios:profiles force:true
bun run store:build-numbers:staging
```

The release lanes also have repository-root wrappers, which hold the bundle's
`VITE_API_URL` and `VITE_APP_URL` to HTTPS on the tier's own host before
running the matching package script:

```sh
./scripts/buildIosRelease.sh            # ios:build-release
./scripts/buildIosStagingRelease.sh     # ios:build-release:staging
./scripts/uploadIosRelease.sh           # ios:upload-release
./scripts/uploadIosStagingRelease.sh    # ios:upload-release:staging
./scripts/buildAndroidRelease.sh        # android:build-release
./scripts/buildAndroidStagingRelease.sh # android:build-release:staging
./scripts/uploadAndroidRelease.sh       # android:upload-release
./scripts/uploadAndroidStagingRelease.sh # android:upload-release:staging
```

All wrappers delegate to `scripts/lib/nativeRelease.sh`. Pass `--help` to any
wrapper for its options. The upload wrappers default to the store's next build
number (see below) and print the number they used.

### Secrets

Production lanes read `.secrets/prod/` and staging lanes `.secrets/staging/`,
unless `NATIVE_RELEASE_SECRETS_DIR` names another absolute folder, as the tests
do; Gradle reads the upload key from the same folder. The lanes load
`shared.env` and then `app.env`, import only the names below (both files also
hold unrelated server values), and never override a variable already in the
environment. Neither file may set the bundle's `VITE_*` hosts.

| File | Contents |
| --- | --- |
| `shared.env` | `TEAM_ID`, `APP_STORE_CONNECT_KEY_ID`, `APP_STORE_CONNECT_ISSUER_ID`, `MATCH_GIT_URL`, `MATCH_GIT_BASIC_AUTHORIZATION`, `MATCH_PASSWORD` |
| `app.env` | `ANDROID_KEYSTORE_STORE_PASS` and `ANDROID_KEYSTORE_KEY_PASS` for the tier's upload key |
| `AuthKey_<APP_STORE_CONNECT_KEY_ID>.p8` | App Store Connect API key |
| `google-play-service-account-admin.json` | Google Play publishing service account |
| `balebase-upload.keystore` | Android upload key (alias `upload`), registered with the tier's Play app |

### Build numbers

By default a release lane's build number is the larger of the latest PR merged
today and the store's next number (the next Play version code or TestFlight
build number), checked against the store when its credentials are available.
The PR comes from `gh`, falling back to local squash-merge subjects like
`(#153)`. Override the date or PR with `ANDROID_RELEASE_MERGED_DATE=YYYY-MM-DD`
and `ANDROID_RELEASE_PR_NUMBER=<number>` (`IOS_RELEASE_*` for iOS), or the
options `merged_date:YYYY-MM-DD` and `merged_pr_number:<number>`.

Set the final number with `build_number:<number>`, or with
`ANDROID_BUILD_NUMBER` or `ANDROID_VERSION_CODE` (the name Gradle reads outside
the lanes) on Android and `IOS_BUILD_NUMBER` or `APPLE_BUILD_NUMBER` on iOS.
Take the store's next number with `next_google_play:true` or
`next_testflight:true`; the upload wrappers do that unless a number, PR, or date
is chosen.

### Google Play

`android build_release` requires the tier's upload key and passwords, runs a
release Capacitor sync, and builds
`android/app/build/outputs/bundle/<variant>/app-<variant>.aab`. The version
name is this package's version.

`android upload_release` uploads that bundle with the tier's service account.
It skips Play metadata, changelogs, images, and screenshots. `track:` defaults
to `internal` (or `GOOGLE_PLAY_TRACK`) and `release_status:` to `completed` (or
`GOOGLE_PLAY_RELEASE_STATUS`). Validate without committing the Play edit with
`validate_only:true`.

### TestFlight

`ios build_release` runs a release Capacitor sync, verifies the generated
native config is fully bundled, installs the App Store certificate and profile
with read-only `match` into a temporary keychain, and builds
`ios/App/output/Balebase.ipa`. Signing requires a Developer Team ID via
`IOS_TEAM_ID`, `APPLE_TEAM_ID`, `DEVELOPMENT_TEAM`, `FASTLANE_TEAM_ID`,
`TEAM_ID`, or `team_id:<id>`, and the `MATCH_*` repository settings. The archive
resolves Swift packages only from the committed `Package.resolved`. The
marketing version is this package's version, as Android's version name is.
`Info.plist` declares that the app uses no non-exempt encryption, so builds
skip the export compliance question.

`ios upload_release` only uploads by default. `changelog:<text>` sets the What
to Test notes, and `distribute_external:true` with `groups:<name,name>`
distributes to external testers, waiting for processing and submitting for
review unless `skip_waiting_for_build_processing:true` or
`skip_submission:true` says otherwise.

The shared `match` repository keeps the team's Apple Distribution certificate
and a `match AppStore <app ID>` profile for each app. `ios profiles` creates a
missing profile or renews an invalid one with the API key; pass `force:true` to
regenerate it, as after the bundle ID's capabilities change. Release builds
only read it.

### Store build numbers

`store_build_numbers` reads the latest build numbers from Google Play (the
`production`, `beta`, `alpha`, and `internal` tracks, or `track:<track>`) and
App Store Connect. Missing credentials or one store's failure do not block the
other lookup.

### Android sideload

`bun run android:install-debug` builds and installs the debug APK on a
connected device; `bun run android:install-release` does the same for the
release APK, after a release Capacitor sync clears any live-reload URL from the
generated native config. `bun run android:sideload` does either, with
`build_type:release` (or `ANDROID_BUILD_TYPE=release`) for the release APK. Set
`ANDROID_SERIAL` when more than one device or emulator is attached.

A release APK signs with the tier's upload key when `ANDROID_KEYSTORE_STORE_PASS`
and `ANDROID_KEYSTORE_KEY_PASS` are exported. Without them, Gradle signs it with
the debug signing config so it can still be sideloaded.

## Android instrumentation tests

```sh
bun run android:test:connected
```

Runs `android/app/src/androidTest` on a connected device or emulator, against
the web build from the last Capacitor sync. `WindowInsetsTest` checks that the
page asks to draw under the system bars and that the WebView ends at the
keyboard. On WebView 140 and later, Capacitor leaves the bars and cutouts to
the page's safe-area padding; older WebViews keep the page clear of them, and
the test checks that the bars' icons contrast with the window background
behind them. CI has no emulator, so run these after changing how the native
shell handles insets. Set `ANDROID_SERIAL` when more than one device is
attached.
